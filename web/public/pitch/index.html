让实验室现有电脑接同一批任务（约 30 秒） 核心表达　我们给已有多台工作站的研究团队提供一套自托管批处理工具。 现场讲法　视觉组换了一个检测模型，需要把同一批图片再跑一遍。现在谁的机器空着、哪台装了对的模型、结果放在哪，往往需要有人协调。CEF 把这些机器接到同一个队列。研究员提交一批图片，设备自动领取任务，结束后在同一个地方看结果。我们拟交付的是实验室内的部署、这套流程和后续维护。 依据　[R1] README、架构与工作空间文档。封面为 ENIAC 历史照片 [V1]。

先算清一批作业的等待和人工成本（约 40 秒） 核心表达　既要看有没有可用算力，也要看有没有值得替换的工作流程。 现场讲法　斯坦福的共享 GPU 资源可能排队，已有优先队列的课题组也有很好的替代方案。EPFL 的实验室说明还保留了另一种日常做法：SSH 登录共享机器，查 GPU 是否忙。我们要找的是两种方案都经常妨碍交付的团队，比如每周要跑推理、不同工作站的空档不好协调。试点前先收两周日志，核对每批等待时长、人工操作分钟、可以挪用的 GPU 时段和实际云账单。 依据　[E1] 斯坦福官方文档，[E2] EPFL 实验室指南，[E3] 高校 GPU 集群预印本。该研究统计的是已运行作业内的平均 SM 利用率，50% 的作业低于 5%，样本为一个高校集群十天、7,399 个作业。这个数字无法换算成目标实验室可调度的空闲小时。 放映：第一步讲校级 GPU。按一下讲组内工作站，再按一下出研究数据。

第一批客户先验证视觉实验室的批量推理（约 45 秒） 核心表达　先找已有数台 GPU、每周反复用同一模型处理数据、还有排队或手工成本的团队。 现场讲法　我们先找一个计算机视觉课题组，把同一数据集用新版 ONNX 模型重跑一遍。图片可以并行处理，检测结果能抽检，还能对照模型版本。使用者是学生和研究工程师，设备管理员或校方 IT 决定能否接入，预算通常要找 PI 或项目负责人确认，再走学校采购。这个角色分工要逐校核实。机器人视觉组如果有同样的离线图像流程，也适合试点。小 AI 团队可能决策更快，有真实云账单的团队可以并行验证付费。已有成熟集群平台的企业团队先放后面。 依据　[R1–R3] 产品及验收，[E1] 校内资源采购与维护角色，[E4] 视觉推理工作流。四种场景的频率和付费判断均为筛选假设。预处理易部署但单机工具便宜，渲染有成熟专用方案，通用资源管理要补齐权限与运维能力。 放映：先扫一眼四个场景。按一下高亮批量推理，再按一下交代使用与采购角色。

多设备协同处理与实测结果（主讲约 70 秒） 一个人提交整批输入，Worker 根据能力和空闲容量领取任务，结果统一返回。我们分别测试了 CPU 缩图和双 GPU 推理，用同一批输入比较两台单机和共同运行，每种条件重复三次，展示中位数。 CPU 测试每批 100 张，共同运行的有效吞吐为每秒 3.3055 张，比最佳单机提高 26.17%，聚合效率为 88.26%。900 个正式输出全部通过逐像素校验。 GPU 测试的 110 张组，共同运行有效吞吐为每秒 2.7463 张，比最佳单机提高 97.36%，接近两条单机实测吞吐之和。但全实验 1350 个输出中只有 1260 个通过固定数值参考，因此这是诊断性结果，数值一致性仍需复验。CPU 提供了完整的输出验收证据，GPU 已观察到共同运行的收益。 指标口径：有效吞吐 P 等于通过校验的输出数除以整轮耗时。逐轮计算 P，取各条件三次中位数后再计算 S 和 η。S 等于共同运行吞吐除以最佳单机吞吐；η 等于共同运行吞吐除以两条单机吞吐之和。η 不表示 GPU 利用率，也不能证明理论最优调度。图中细线为三次最小至最大值，不是置信区间。 等待时间备查：CPU 的 jochi、liusic、共同运行分别为 38.17、88.85、30.25 秒，共同运行相对耗时较短单机减少 20.74%。GPU 110 张分别为 70.08、79.05、37.50 秒，减少 46.48%。GPU 的有效吞吐最佳单机是 liusic，取得全部返回结果更快的单机是 jochi，两个比较不能混用。 规模与正确性：GPU 的 8、32、110 张是固定 110 张测量集的嵌套子集。三种规模的 η 分别为 77.16%、92.21%、99.97%。8 张组三条件各三次共 72/72 通过；110 张双机三次共 306/330 通过。全实验未通过的 90 个输出均来自 jochi，涉及 15 张不同输入。参考容差为置信度 0.002、框坐标 0.3 像素，并要求检测数量和类别一致。这是数值一致性检查，不是识别准确率或 mAP。 计时范围：CPU 包含逐轮输入上传；GPU 复用已注册数据集，不含首次注册。两组均包含调度和结果下载，不计本地参考校验，不能直接比较 CPU 与 GPU 硬件性能。GPU 实验跨一次客户端连接中断恢复完成，中断轮次的旧计时已排除。上游精度修复尚未在这组数据上复验。物理设备身份、完整硬件和远端部署提交仍需补证。Blender 未在这两组实验中验收。 数据来源：CPU 与 GPU 数据依据下方报告和精简数据链接。

替代方案（约30秒） 单机能完成就不必引入分布式，缺显存或需要稳定弹性资源时云更合适。CEF的切入点是已有设备的小团队，希望减少反复分发与收结果。接入成本、人工节省和持续使用意愿仍待验证，不宣称独有调度技术。技术答辩备查：HTCondor可利用空闲桌面，BOINC支持志愿计算，Slurm/Run:ai支持成熟资源管理，Ray支持开发工作流，Flamenco/Deadline服务渲染。它们是不同层次的替代方案；是否比这些方案易用需实测，不能用这一页证明优势已成立。

商业路径（约45秒） 开源是产品基础。代码采用MIT许可，但仓库当前私有，公开发布是计划，不在这次改版自动公开。实验室和开发者可自行部署，不向其预设软件订阅。愿意为交付、集成和保障付费的组织，可以选择部署运维服务；国企等是可能的技术合作方向，不是已有客户。进入这类组织需补权限、审计、内网交付与支持能力。 另一条更长期路径是让个人出租授权闲置算力，平台撮合任务并探索服务费。今天只有受控团队池，没有交易和结算。目标是比云服务更低的有效任务成本，而非只看GPU小时报价。总成本包含设备主收益、电费、带宽、折旧、失败重试和平台运维，需在同等输出质量下与云比较。数据隔离、结果验证、计量结算、设备退出与服务稳定性是前提，没有证据就不承诺固定折扣。两条路径分别验证，不假设一定成功。

结尾（约30秒） 当前核心服务已能运行，但规模化运营和商业化尚未验证。第一步用课程及开发者社区触达使用者，观察重复使用、输出正确性和设备接入难点。第二步只有真实出现付费交付需求才开展组织试点，算清每次部署与后续支持成本。第三步交易需要新的安全与运营能力，不能把团队内可信计算直接等同于公开市场。我们希望找到愿意带授权设备和真实任务试用、贡献代码，或共同探索组织技术服务的伙伴。未来目标是降低正确完成任务的总成本，而不是宣称硬件免费就一定更便宜。
