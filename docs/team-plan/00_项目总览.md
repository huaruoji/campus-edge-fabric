# D 赛题｜校园文档工坊：四人技术团队两天执行总览

> 人员口径：4 人做技术，商业化另有第 5 人独立负责。当前任务包仅安排 4 位技术成员，商业化不进入两天排期、技术交付或验收，也不是开发前置条件。将 A—D 替换成姓名即可分发。本文是实施计划，不代表功能已经实现或性能已经验证。

## 1. 项目目标与范围

为校园课题组或课程团队提供批量 OCR 服务：用户上传一批扫描图片，两台真实电脑分担识别，统一查看进度、预览文字并下载结果。

**两天目标：先按这份总览把技术项目做出来。第一天跑通真实双机闭环，第二天完成异常处理、性能证据和技术演示。**

开工先由四人共同确认总览中的范围、接口和里程碑，然后并行推进。每人的工作都以同一条闭环验收：上传新图片 → 两台真实设备处理 → 结果回传 → 预览与下载。

| 必须交付 | 有余力再做 |
| --- | --- |
| JPG/PNG 多文件上传，清晰中英文印刷体 OCR | PDF 自动拆页 |
| 两台独立物理设备在同一批次实际处理有效任务 | GPU 加速、更多节点 |
| 进度、原图与文字对照、结果下载 | 搜索、摘要、问答 |
| 节点状态、失败原因、手动重试 | 自动迁移、复杂调度 |
| 单机 A、单机 B、双机的正确吞吐量对照 | 复杂可视化、账号与计费系统 |

正式比赛的允许准备范围以主办方规则为准。区分提前完成与比赛期间完成的工作。所有设备必须获得所有者授权。

## 3. 最小架构与协作约定

```text
用户浏览器
    │ 上传 / 查询 / 下载
    ▼
中央服务：FastAPI + SQLite + 文件目录（部署于电脑 1）
    ▲                                  ▲
    │ 主动领取 / 下载 / 回传            │ 主动领取 / 下载 / 回传
电脑 1：Worker + 本地 OCR          电脑 2：Worker + 本地 OCR
```

- 一张图片对应一个任务；每台 Worker 起步只同时处理一张。
- 初版中央服务使用单进程；数据库事务保护领取与状态修改。
- Python + FastAPI；OCR 初版使用 Tesseract + pytesseract，CPU 路线。
- B 在第一天上午用真实样张验证质量。若需更换 OCR 引擎，保留统一 `recognize(image, language, timeout)` 适配边界。
- 前端每 2 秒查询一次；心跳建议每 3 秒发送一次，超过 15 秒无心跳标记失联。参数可配置。
- OCR 初始超时为 60 秒，按实测调整；心跳与 OCR 独立运行。
- Worker 只需主动访问中央服务；无需在 Worker 上开放远程执行接口。
- 中央入口使用访问凭据，Worker 使用独立设备凭据。仅在受控网络开放必要服务，密钥不入库、不进日志。
- 时间戳采用带时区的 ISO 8601；耗时统一毫秒，内存统一 MB。

## 4. 接口契约 v1

第一天 10:00 前四人确认此契约。A 实现接口，B/C 按契约调用，D 据此编写测试。任何字段修改先通知 B/C/D 并同步示例。

### 4.1 公共字段与状态

- 所有 ID 为不透明字符串，前端与 Worker 不解析其格式。
- 任务字段：`task_id`、`filename`、`position`、`status`、`worker_id`、`attempt`、`duration_ms`、`error`。
- `position` 从 1 开始，按用户提交顺序排列；下载不按完成先后排序。
- 未执行时 `worker_id`、`duration_ms` 为 `null`，`attempt` 为 0；每次成功领取时递增 `attempt`。
- 任务状态：`queued`、`running`、`succeeded`、`failed`、`interrupted`。
- 节点在线由心跳判断；忙闲独立记录，不能用“忙”代替“在线”。
- 批次返回 `counts`，包含 `total` 以及五种任务状态的计数；计数之和必须等于 `total`。
- 批次不单独维护复杂状态，前端根据计数展示：进行中、已结束、或需要处理。存在 `failed/interrupted` 时不能显示“全部成功”。

### 4.2 接口表

| 方法与路径 | 调用方 | 请求 | 成功响应 |
| --- | --- | --- | --- |
| `POST /api/batches` | C | multipart，多个 `files` 字段 | `201`：`batch_id,total` |
| `GET /api/batches/{id}` | C | 批次 ID | `200`：`batch_id,counts,tasks` |
| `GET /api/tasks/{id}/input` | C/B | 任务 ID；校验访问权限 | `200`：图片字节 |
| `GET /api/tasks/{id}/result` | C | 任务 ID | `200`：`task_id,status,text,worker_id,attempt,duration_ms,error` |
| `GET /api/batches/{id}/download` | C | 批次 ID | `200`：ZIP，包含成功结果和全部任务清单 |
| `POST /api/tasks/{id}/retry` | C | 空 JSON；仅失败/中断任务可重试 | `200`：更新后的任务对象 |
| `GET /api/workers` | C | 无 | `200`：`workers` 数组 |
| `POST /worker/register` | B | `node_name,os,cpu,memory_mb,ocr_version,languages` | `200`：`worker_id` |
| `POST /worker/heartbeat` | B | `worker_id,current_task_id,cpu_pct,memory_used_mb` | `200`：`accepted:true` |
| `POST /worker/claim` | B | `worker_id` | `200`：任务；无任务为 `204` |
| `POST /worker/result` | B | 见示例 | `200`：`accepted:true` |

`workers` 数组每项至少包含：`worker_id,node_name,online,busy,last_seen,cpu_pct,memory_used_mb,completed_count`。尚无有效采样时利用率为 `null`，前端显示“暂无数据”。

`result` 未成功时 `text` 为 `null`，不伪造文字。下载 ZIP 中的 `manifest.csv` 保留所有任务及失败原因；只有成功任务生成文字文件。

### 4.3 领取与回传示例

领取响应：

```json
{
  "task_id": "task_001",
  "attempt": 1,
  "input_url": "/api/tasks/task_001/input",
  "ocr": {"language": "chi_sim+eng", "timeout_seconds": 60}
}
```

成功回传：

```json
{
  "worker_id": "worker_a",
  "task_id": "task_001",
  "attempt": 1,
  "status": "succeeded",
  "text": "识别得到的文字",
  "duration_ms": 2350,
  "error": null
}
```

失败回传使用同一结构，`status` 为 `failed`，`text` 为 `null`，`error` 为 `{"code":"OCR_TIMEOUT","message":"识别超时"}`。

### 4.4 错误、幂等和权限

- 浏览器请求使用 `Authorization: Bearer <DEMO_TOKEN>`；Worker 使用 `Authorization: Bearer <WORKER_TOKEN>`。示例是占位符。
- Worker 仅下载分配给自己的当前任务图片；浏览器凭据不能调用 Worker 管理接口。
- 统一应用错误正文：`{"code":"错误代号","message":"可读说明"}`；A 统一处理校验异常。
- `401/403` 鉴权或权限失败；`404` 未找到；`409` 非法状态或过期尝试；`413` 上传超限；`422` 参数或文件不合法。
- 领取必须原子完成，不能让两个 Worker 领取同一当前任务。
- 回传校验 `task_id + worker_id + attempt` 和当前状态。已接收结果的相同重发幂等确认，不增加计数；冲突结果返回 `409`。
- 节点失联后当前任务进入 `interrupted`。旧尝试迟到回传不恢复为成功，返回 `409`；用户重试后重新排队，新领取产生新尝试编号。
- 自动迁移不属于本版必做内容；网络中断后的重复计算不计入有效吞吐。

## 6. 测试与性能口径

1. 开发样本与最终测量样本分开；输入须有合法来源，包含可人工校对的标准文字。
2. 第一天下午由 B/D 确定识别支持范围、文本规范化和质量门槛，在正式测量前冻结。可采用字符错误率，公式为字符编辑距离除以标准文字长度；空白页单独判定，不作零分母计算。阈值是团队实验假设，不是赛事官方规定。
3. 程序“执行成功”和“识别正确”分开：非空输出不等于正确结果。
4. 三组测试：电脑 1 单机、电脑 2 单机、双机。固定每台设备的引擎、预处理、线程与并发，输入类型和分布可比。各组预热后重复三次，保存全部结果。
5. 单机从本地输入开始处理至结果落盘；双机从中央服务开始供给已就绪任务至结果收齐，包含 Worker 传输开销。用户初次上传耗时另记。所有报告明确该边界。
6. 用测试开关或启动顺序保持正式计时前 Worker 不领取，正式开始后再开放队列；不得把提前完成任务算进窗口。
7. 有效吞吐 `P = 正确且唯一完成的页数 / 测量秒数`。失败、重试的重复计算和重复回传不重复计数。
8. 聚合效率 `η = P_pool / (P_1 + P_2)`；相对最强单机提升 `S = P_pool / max(P_1,P_2)`。分母为零时报告不可计算。
9. 每台设备每秒采样 CPU 与内存，报告整个测量窗口的平均值；所有承担计算的设备必须列出。中央服务与 Worker 同机的开销也要说明。
10. 不设预定加速百分比。若收益不明显，报告任务粒度、网络、线程争抢或中央服务瓶颈；不挑选最好结果替代完整报告。
