# Procedure：两台 Worker 各自运行与共同推理

这组实验回答：同一批输入、同一模型和输出质量要求下，小组通过同一个 Coordinator 使用两台电脑，能否比任一电脑单独服务更快取得全部结果。测试设备为远程 Worker；D 的电脑只负责提交、计时、下载及校验，不计作第三台 Worker。

## 1. 前提与固定输入

- 使用仓库已有 `infer` 适配器和 YOLO11n ONNX 模型，参数为 `imgsz=640, conf=0.25, max_det=100`。
- 固定模型 SHA256：`b1a053916c9d667d05a53bfb43764a0aabb11dee20795af75b8ce408760685d3`。
- 输入来源及授权见 [数据集说明](../../benchmarks/datasets/README.md)。使用固定 COCO128 图片划分：冒烟 8 张、预热 8 张、正式 110 张，三个集合互不重叠，每个文件不超过 500,000 字节。
- 正式图片按种子 `20261114` 打乱，取前 8、32、110 张作为嵌套子集。同一规模的所有条件使用完全相同的输入顺序；每张图片均核对本地清单 SHA256。
- 本地 CPU 参考由同一模型、同一输入和参数生成。置信度容差 0.002、框坐标容差 0.3 像素，要求检测数量与类别一致，以一对一匹配处理输出排序差异。参考生成不作为单机性能条件。

## 2. 选择设备并确认实际后端

```powershell
python benchmarks/infer/run_gpu_benchmark.py --auto-workers
python benchmarks/infer/run_gpu_benchmark.py --run --auto-workers
```

第一行仅做离线检查；第二行隐藏输入 Token 后联网。若此前有中断的任务，附加 `--previous-job <保存的 Job ID>`，不要直接重复提交。

自动模式读取当前设备状态，从在线、infer 可用且上报固定模型哈希的 Worker 中选至多两台，优先声明 CUDA 的设备。所有新任务都用 `worker_ids` 限定为选中的单台或两台；其他在线节点不能参与。

先对每台各提交一个 8 张冒烟作业，以结果中的 `provider` 确认实际 CPU/CUDA 后端，同时校验文件与数值。随后固定每个 Worker 的后端映射；任何后端、模型、身份、slots 或配置变化都会停止实验。只有一台兼容设备时先完成其冒烟，不生成双机性能结果。脚本不远程安装依赖或切换 Worker 配置。

Worker 能力自报、结果 provider 与数值一致性是本组记录的证据。GPU 型号、显存、独立物理电脑身份、部署代码版本及实际 GPU 算子跟踪需由设备操作者补充，不能从设备名称推定。

## 3. 正式对照

| 项目 | 设计 |
| --- | --- |
| 条件 | single-1、single-2、pool：第一台、第二台、两台共同服务 |
| 规模 | 8、32、110 张 |
| 重复 | 每个规模、每个条件重复 3 次，共 27 个正式作业 |
| 总输出 | 正式 1350，另有冒烟 16、预热 288；不是 1654 张不同原图 |
| 顺序 | 每次重复轮换规模和条件顺序；完整计划在运行前保存 |
| 预热 | 每个正式作业前先跑独立的 8 张预热；pool 前分别预热两台，共 36 个预热作业 |
| 输入传输 | 各固定输入组注册为 dataset 后复用，不逐轮上传 |
| 并发配置 | 使用记录的 Worker slots；轮次前后核对，不在中途调参 |

测量期间保持两台在线，不更新部署、不切换推理环境、不运行其他池作业。客户端会查询可能占用所选设备的排队/运行任务，但检查与提交之间仍存在时间窗口，无法代替团队配合。未选设备上无法派发到所选设备的旧任务不阻止此次测试。

小批次 pool 可能只由一台完成。这种轮次仍保留，并明确记录实际贡献；不能反复重跑到两台都有结果为止。

## 4. 时间与指标

主要指标为 **通过校验的图片数 / 客户端提交作业至结果 ZIP 下载完成的墙钟时间**。自动模式使用已注册 dataset，首次数据集注册不计时；本地参考生成和下载后的数值校验也不计时。轮询、资源采样、网络往返及期间客户端开销包含在总时间中。

另存提交请求耗时、提交至观察到终态的耗时、下载阶段耗时和服务端作业起止时间。服务端作业窗口与客户端各阶段可能重叠，不能把这些时间直接全部相加，也不能把计算以外的差额全部叫作网络耗时。

每个规模、每个条件取三轮吞吐中位数，同时保留最小值和最大值：

```text
S = P_pool / max(P_single_1, P_single_2)
eta = P_pool / (P_single_1 + P_single_2)
```

`S > 1` 表示该规模下观察到双机优于最快单机。单机吞吐之和只是经验参照，eta 不能解释为与理论最优调度的距离。三个重复不足以支撑普遍性能保证；只描述实测规模，不外推出确定的收益阈值。

这套时间口径与此前逐轮上传输入的 thumbnail 测试、网页内置评测不同，不能直接拼接为同一性能曲线。比较的是两台电脑及其部署、网络和服务路径，不是不同 GPU 芯片的纯算力排名。

## 5. 验证、故障与交付

每轮检查任务状态、输入/任务/Worker 对应关系、ZIP CRC、输出清单、SHA256、provider 和 CPU 数值参考。统计实际有效输出，不把失败或重试次数计作新增工作。COCO128 属于训练子集；这里验证工程输出一致性，不测 mAP 或泛化精度。

严格验收默认遇到数值不一致即停止。若明确进行诊断性对照，可增加 `--record-numerical-mismatches`：数值阈值保持原值，所有轮次继续记录通过/未通过数，未通过项不计入有效吞吐，整轮耗时完整保留。文件结构、哈希、provider、设备配置或作业失败仍立即停止。诊断结果保存在独立的 `diagnostic-auto-infer-<时间>/`，报告必须同时展示数值通过率，不能声称全输出正确或将它当成完整正确性验收。

整机资源心跳按作业时间窗去重汇总。短作业可能缺采样，保留缺失值；整机占用也可能包含其他程序，不能据此推断本任务 GPU 利用率或显卡已饱和。

错误或超时后保留 Job ID 与已有证据，脚本不自动重提或取消。客户端退出不代表服务端任务已停止；恢复前先查旧作业。若旧作业仍可能使用所选设备，自动模式等待最多 90 秒再停止新提交；不会把跨故障等待补算成有效的正常性能轮次。

对于已记录的网络中断，可用 `--run --resume <原运行目录>` 从断点继续。恢复入口重验已有结果和计划前缀，核对原 Worker 配置，先查询、下载未归档的旧作业，再补剩余轮次；不会重跑已完成的正式轮次。跨中断的旧计时及提前做过的预热移入 `continuations` 保留，恢复后重新冒烟、预热，报告须说明分段测量。只读请求的短暂传输异常最多尝试四次，提交请求不自动重试；当轮发生的重试耗时包含在完整计时内。

运行证据在 `data/d-acceptance/auto-infer-<时间>/`。`progress.json` 记录进度，完成后生成 `summary.json` 和初步报告。完整运行再执行：

```powershell
python benchmarks/infer/curate_report.py data/d-acceptance/auto-infer-<时间>
```

整理程序重新校验所有 65 个结果 ZIP、固定输入、配置和轮次清单，重算指标后输出中文报告、PNG/SVG 对比图及精简 JSON。未完成的实验不能生成完整性能报告。Git 仅保留可复跑脚本、Procedure、报告、图表和筛选后的证据；原图、模型、原始 ZIP、逐任务日志和 Token 留在本地。
