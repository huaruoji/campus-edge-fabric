# B｜Worker、OCR 与部署工作清单

负责人：______　协作人员：A（后端）、C（前端与交互）、D（测试与验收）

> 你的目标是让两台获得授权的物理电脑真实处理同一批 OCR 任务，并提供可核验记录。完整接口见[项目总览](00_项目总览.md)第 4 节。

## 1. 你的交付范围

- `worker/`：OCR 适配器、注册、心跳、领取、下载、处理、回传。
- `tests/worker/`：识别、损坏输入、超时、网络失败测试。
- `scripts/`：两台设备可用的启动脚本和检查步骤。
- 单机测量运行器、两机配置清单、处理日志、CPU/内存采样。
- 两机联网和运行环境；向 D 提供部署说明、真实设备信息和测量记录，向 C 提供节点字段样例。

## 2. 环境与网络清单

- [ ] 确认两台独立物理设备均获授权，记录系统、CPU、内存和设备名称。
- [ ] 两台电脑接通同一受控网络；验证 Worker 可以访问中央服务。
- [ ] 仅为必要服务配置合适的网络访问，不开放任意 Shell 或无鉴权远程桌面。
- [ ] 安装 Python 依赖、Tesseract 引擎及 `chi_sim/eng` 语言数据。
- [ ] 两台分别检查 OCR 路径、语言列表和真实图片识别结果。
- [ ] 第一日上午决定 OCR 引擎是否满足声明场景；如需替换，与 A/C 同步并保留统一适配接口。
- [ ] 准备并验证备用网络方式，避免校园 Wi-Fi 客户端隔离。
- [ ] 用配置提供 `SERVER_URL`、`WORKER_TOKEN`、节点名和 OCR 路径，不硬编码密钥。

## 3. Worker 实现清单

```text
自检环境 → 注册节点 → 独立心跳
                       ↓
领取任务 → 下载图片 → 本机 OCR → 回传结果 → 继续领取
```

- [ ] 启动先检查中央连接、OCR 引擎和语言数据，缺项给出清晰错误。
- [ ] 初始每台只处理一个任务；不要让空闲领任务请求形成密集循环。
- [ ] `claim` 返回 `204` 时短暂等待后再请求。
- [ ] 领取后保存 `task_id` 和 `attempt`，所有回传使用原值。
- [ ] 按返回配置识别语言、超时；输出文字和实际 OCR 耗时。
- [ ] 心跳约每 3 秒独立发送，OCR 阻塞时仍正常工作。
- [ ] 单图超时终止对应识别进程，回传 `failed` 与可读错误。
- [ ] 损坏图、下载失败、引擎错误均记录，不把失败当成空文字成功。
- [ ] 网络失败采用有间隔、有上限的请求重试；重复回传保持同一任务与尝试编号。
- [ ] 遇到 `409` 旧尝试响应，记录结果失效，不无限回传。
- [ ] 记录节点、任务、尝试、文件摘要、开始/结束与结果摘要，不记录密钥。
- [ ] 退出尽可能停止本机在途 OCR；真正失联情况下由后端标记并人工重试。
- [ ] 每秒采样 CPU 和内存到本地日志，定期随心跳上报。

资源利用率说明：CPU 数据描述忙碌程度，不代表正确吞吐；首个无效采样标记为空，不能填造假数值。

## 4. 与 A 的接口对接

| 接口 | 你发送/接收什么 |
| --- | --- |
| `POST /worker/register` | 发送节点名、OS、CPU、内存、OCR 版本和语言；保存返回的 `worker_id` |
| `POST /worker/heartbeat` | 节点 ID、当前任务或 `null`、CPU、内存 |
| `POST /worker/claim` | 发送节点 ID；接收任务 ID、尝试编号、相对图片 URL 与 OCR 配置 |
| `GET /api/tasks/{id}/input` | 携带 Worker 凭据下载分配给自己的图片 |
| `POST /worker/result` | 发送节点、任务、尝试、状态、文字或错误、毫秒耗时 |

第一天 10:00 前和 A 固定契约；注册重试与重启后的节点身份识别也需对齐。相对图片路径拼接中央服务地址，不把它当作本地路径。

## 6. 第二天工作与交付

- [ ] 09:00—11:00：验证超时、损坏图、网络失败、退出及重启；配合 A 检查失联与旧结果。
- [ ] 两台设备用一致的引擎版本、语言数据、预处理；记录各自线程与并发配置。
- [ ] 11:00—12:00：与 D 冻结测量输入、正确性标准、资源采样和预热流程。
- [ ] 13:00—15:00：执行电脑 1 单机、电脑 2 单机、双机测试，配合各组三次重复。
- [ ] 向 D 交付全部单机结果、逐任务日志和 CPU/内存采样，不只交最好一次。
- [ ] 记录双机期间中央服务与 Worker 同机运行的开销和可能瓶颈。
- [ ] 15:00—17:00：完成配置、启动说明、常见错误与备用网络步骤。
- [ ] 19:00—20:00：两台重启后按文档恢复服务，彩排暂停 Worker 并展示反馈。

## 7. 单机测量要求

- 单机运行器复用同一个 OCR 适配器和配置，不另外写一套更快或更简单的识别流程。
- 同类输入、同一质量标准、可比输入分布；预热后开始计时。
- 保留每页输出，由 D 的校对脚本判定是否合格；非空结果不能直接算正确。
- 记录整个测试起止与总耗时，不把各任务耗时相加冒充并行服务耗时。
- 测量样本应让设备持续有任务，输入规模按实际速度调整。
- CPU 与内存采样覆盖完整测试窗口，不能只挑忙碌时段。

## 8. 最终自检

- [ ] 两台物理设备都能独立识别、联网领取和回传。
- [ ] 有证据证明同批任务由两台设备真实完成。
- [ ] OCR 进行中仍有心跳，超时有反馈。
- [ ] 出错后程序不密集重试、不伪报成功。
- [ ] 两机环境、测量日志、启动脚本已交给 D。
- [ ] D 得到完整设备配置与测量边界，能复现单机和双机测试。

**工作优先级：两机各自 OCR → 远程领取回传 → 独立心跳与日志 → 测量与部署可靠性。** 不把时间耗在非必要 CUDA、复杂组网或容器编排上。
